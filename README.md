# 投稿ランチャー（XXX_automatic）

GitHub Pages で公開している学習アプリを題材に、**X と note の投稿を「文章・画像・ハッシュタグ・URL がぜんぶ用意された状態」まで自動で作る**仕組みです。

人がやるのは、スマホで通知を開いて **カードをタップ → 投稿ボタンを押す** だけ。

**費用は月0円**です。

---

## なぜ作ったか

発信が続かないのは意志の問題ではなく、毎回この3つが必要になるからです。

1. 何を書くか考える
2. 文章を書く
3. 画像を用意する

この3つを丸ごと機械に渡し、人には「出す/出さない」の判断だけを残しました。

---

## しくみ

```
⓪ 反映   先週ぶんの「反応よかった」を取り込み、終わった週を履歴に移す
① 収集   GitHub API で全リポジトリの README・MANUAL を集める
①'' 収集 アプリのリポジトリに書き上げてある note 記事があれば、貼れる形にして運ぶ
①' 調査  いま教育の現場で何が話題かを検索で拾う（学校の行事暦と合わせて題材を選ぶ）
② 理解   Gemini がアプリごとの「プロフィール」に整理する（更新が無ければ再生成しない）
③ 素材   Playwright が各アプリを開いてスクショ → 紹介カード画像を作る
③' 素材  note の主題アプリを実際に操作して、記事に入れる画面を撮る
④ 生成   1枠につき3案書かせ、編集者役が読者の目で1つ選ぶ
　 　　　 反応がよかった1本は、別の言い方にして出しなおす（生成を呼ばずに1枠埋まる）
　 検査   ガードレールにかける（個人情報・誇大表現・字数・本文のリンク・収益化表現）
　 　　　 落選案にも同じ検査をかけ、先月と似すぎた文章は書きなおさせる
⑤ 配信   ランチャーのデータとアプリ一覧ページを作って GitHub Pages へ
⑥ 通知   枠ごとに GitHub Issue が立つ → スマホに通知が届く（朝6:30 / 夜20:00）
⑦ 投稿   ①本文を共有 → ②リンクを返信に置く（ランチャーが順に案内します）
⑧ 記録   ［投稿した］と［反応よかった］を［まとめて送る］→ ⓪ に戻る
```

⓪〜⑥は GitHub Actions が日曜の夜と、投稿の枠ごと（朝・夜）に自動で回します。
人がやるのは ⑦ と ⑧ だけです。

週次が失敗したときは、その旨の Issue が立ちます。
下書きが尽きた日には、［いま出す］タブに用意してある予備から2件を提案します。
**気づかないうちに発信が止まることが無いようにしてあります。**

### 待たずに作らせる（つくる）

上の流れは日曜の夜を起点にしています。ところが
「このアプリの話を、いま出したい」は予定と関係なくやってきます。

ランチャーの **［つくる］** タブで、52件のなかからアプリを1つ選び、
本数（2〜6本）・型・切り口を決めて頼むと、1〜2分でその場に並びます。
アプリ一覧のページからも、選んだ状態でそこへ来られます。

```
アプリを選ぶ → 頼む → GitHub の［Create］を押す
  → ワークフローが作る → 検査 → 端末に届いて貯まる → 好きなときに出す
```

作らせた投稿は**その端末に貯まります**（書き出して別の端末に移せます）。
出すのは好きなときで、週の投稿とまったく同じように画像を選んで共有できます。

> 文章を作るのに Gemini を使いますが、API キーを画面に持たせるわけにはいきません
> （docs/ は公開されます）。そこで注文を Issue にして送り、
> ワークフローが作った結果を GitHub Pages 経由で受け取っています。
> 反応の記録と返信の下書きも、まったく同じ理由で同じ道を通っています。費用は 0 円のままです。

## 本文にリンクを入れていない理由

X は、**本文に外部リンクがある投稿のリーチを大きく下げます。**
リンク付きの投稿は本文だけの投稿に比べて 30〜50% 表示が減り、
Premium でないアカウントでは 2026年3月以降ほとんど埋もれます。

そこで、**本文はリンク無しで書き、リンクは自分への最初の返信に置いています。**

```
① 本文（リンクなし・画像つき）を投稿する
② その投稿に返信する形でリンクを置く
```

ランチャーが ①②③ を順に出すので、押していけば終わります。

> 費用の面だけを見れば、本文に URL を入れても困りません（X API を使っていないので）。
> それでも外しているのは、読まれないなら発信した意味がないからです。
> `config/guardrails.json` の `urlPlacement` を `"body"` にすれば元に戻せます。

## X API を使っていない理由

**2026年2月に X API の無料枠が廃止されました。** 現在は従量課金のみで、
URL を含まない投稿が $0.015、**URL を含む投稿は $0.20**（1投稿あたり約32円）かかります。
毎日3投稿すると月3,000円近くになります。

代わりに **Web Share API** を使っています。

```js
navigator.share({ files: [カード画像], text: 本文 })
```

これを呼ぶと OS の共有シートが開き、X を選ぶと**画像が添付され本文が入った状態**の
投稿画面が立ち上がります。API も課金も要りません。

X の Web Intent（`x.com/intent/post`）は本文を入れられますが**画像を添付できない**ため、
PC や共有シート非対応の環境向けのフォールバックとして併用しています。

### 添付する画像を選ぶ

X は1投稿に画像を4枚まで載せられます。ランチャーの各投稿には候補のサムネイルが並び、
タップした順に最大4枚まで添付されます（選択はその端末に残ります）。

候補は2種類です。

- **紹介カード** … このシステムが作る 1200×675 の画像（既定で選ばれています）
- **アプリのリポジトリに置いてある画像** … note の記事のために撮ったスクリーンショット
  （`docs/note/images/01-home.png` のような形）。実際にアプリを操作した画面なので、
  自動撮影では作れない中身になります。`npm run collect` が置き場所を問わず拾い、
  記事本文の `![音読の画面]` や README の一覧表から説明文も一緒に持ってきます。

リポジトリ側の画像は**このリポジトリに取り込まず**、`raw.githubusercontent.com` から
直接読みます（コミット SHA で固定）。取り込むと1アプリで数MBになり、
毎週コミットするぶんだけリポジトリが重くなるためです。その代わり、
圏外では画像を添付できません（本文だけの共有になります）。

### リポジトリに用意した記事を出す

アプリを作ったときに、そのリポジトリの中で note の記事まで書き上げていることがあります。
たとえば KANJI_Town の `docs/note/` には、本文（約7,900字）と、
実際にアプリを操作して撮った画面が27点、貼る手順を書いたメモが置いてあります。
**機械が書いた下書きより中身が濃いのに、これまでは手作業のまま残っていました。**

いまは週次がそれを見つけて、ランチャーの **note** タブに並べます。

```
アプリの repo の docs/note/*.md
  → ①'' 収集（貼れる本文と、画像の並びに分ける）
  → docs/note-articles/<アプリ名>.json として配信
  → note タブに「リポジトリに用意された記事」として出る
```

- 本文は note に貼れる形（`##` などの記号を落としたもの）でコピーできます
- 画像を入れる位置には `［画像1: トップページ］` という目印が入ります
- **画像は上から1枚ずつ共有シートに渡せます。** 番号は本文の目印と同じです
- 画像のすぐ下の一文は、note のキャプション欄に貼れるよう別に取り出してあります
- 記事は**書きかえません**。連載の書き方から外れているところは、
  カードに並べて出すだけにしてあります（直すかどうかはご自身で決めるためです）

画像はこのリポジトリに取り込まず、アプリのリポジトリから直接読みます
（1本ぶんで数MBあり、毎週コミットするとリポジトリがそのぶん重くなるためです）。
URL はコミット SHA で固定してあるので、画面に出ている絵と渡す絵が食い違うことはありません。

## note を自動投稿しない理由

note に公式 API はありません。非公式 API は存在しますが、利用規約に触れて
**アカウント停止につながる可能性**があります。本業の信用に関わるため使っていません。

代わりに、本文を生成してクリップボードに入れ、note のエディタを開くところまでを自動化しています。
公開ボタンは人が押します。**画像を上げる口も無い**ので、
リポジトリに用意した記事の画像は「1枚ずつ共有シートに渡す」形にしてあります。

## はじめかた

### 1. Gemini API キーを取る（無料・カード登録不要）

<https://aistudio.google.com/apikey> でキーを作ります。

リポジトリの **Settings → Secrets and variables → Actions → New repository secret** で、
名前を `GEMINI_API_KEY` として登録します。

### 2. GitHub Pages を有効にする

**Settings → Pages → Source** を **GitHub Actions** にします。

### 3. 最初の1回を手で動かす

**Actions → 週次 — 翌週の投稿を用意する → Run workflow**

初回は全アプリのプロフィール生成とスクリーンショット撮影が走るので、20〜30分ほどかかります。
2回目以降は更新のあったアプリだけになるので数分で終わります。

### 4. スマホのホーム画面に追加する

<https://gigayama.github.io/XXX_automatic/> を開き、「ホーム画面に追加」します。

### 5. GitHub モバイルアプリの通知をオンにする

毎朝の Issue が通知として届きます。ここが発信を続けるための要です。

### 6.（任意）Discord に通知する

Discord サーバーの Webhook URL を `DISCORD_WEBHOOK` という名前の Secret に登録すると、
毎朝 Discord にも画像つきで届きます。通知の見え方はこちらのほうが快適です。

## 調整のしかた

いちばん触るところから順に並べてあります。

| 変えたいこと | どこを直すか |
|---|---|
| 投稿の文体・話し方 | `CLAUDE.md` の §3（そのままプロンプトに入ります） |
| 1日の投稿数・時間帯 | `config/slots.json` |
| 誰に向けて書くか・最初の1行の型 | `config/audience.json` |
| 時期ごとの困りごと（学校の1年） | `config/calendar.json` |
| リンクを本文に入れるか返信に回すか | `config/guardrails.json` の `urlPlacement` |
| 投稿の型（切り口） | `config/themes.json` |
| note の記事の文体・構成 | `config/note-style.json` |
| 禁止表現・字数の基準 | `config/guardrails.json` |
| 題材にしないリポジトリ | `config/accounts.json` の `excludeRepos` |
| 使う Gemini のモデル | `config/accounts.json` の `geminiModel`（既定は `auto`） |
| 1投稿に複数枚の画像を付ける | `config/media.json` の `carousel.enabled` |
| 反応がよかった投稿を出しなおす間隔 | `config/themes.json` の `rotation.repriseAfterDays`（既定30日・0で無効） |
| 過去とどこまで似てよいか | `config/guardrails.json` の `maxSimilarityToPast` |
| 収益化のオン/オフ | `config/monetization.json` |

`CLAUDE.md` を直せば、翌週から投稿の雰囲気が変わります。

### Gemini のモデルは自動で最新になります

`config/accounts.json` の `geminiModel` は既定で `"auto"` です。
毎週の実行時に「いま使えるモデル」を API に聞いて、**いちばん新しい安定版**を選びます。

`gemini-3-flash` のような新しい版が出たら、**設定を書き換えなくてもそちらに移ります。**
古い版が止められて 404 になる、という止まり方も防げます。

```bash
node scripts/check-gemini.mjs           # いま何が選ばれるかを確かめる（実際に1回投げる）
node scripts/check-gemini.mjs --models  # 選べるモデルを良い順に並べる
```

選ばれた結果は `data/gemini-model.json` に残ります。コミットしているので、
**いつどの版に切り替わったかが git の履歴で分かります。**

| したいこと | どうするか |
|---|---|
| 版を固定したい | `geminiModel` にモデル名を直接書く（例: `"gemini-2.5-flash"`） |
| 文章の質を上げたい | `geminiModelPrefer` を `"pro"` に（無料枠の上限に当たりやすくなります） |
| 新しい版をいち早く試したい | `geminiAllowPreview` を `true` に（preview は予告なく変わります） |

## 収益化について

`config/monetization.json` の `enabled` は既定で `false` です。

日本の公立学校教員は地方公務員であり、兼業・副業には
**地方公務員法38条にもとづく任命権者の許可**が必要な場合があります。手続きは自治体ごとに異なります。

確認が済むまでは収益化の導線を一切出さない設計にしてあり、
`scripts/lint-drafts.mjs` が生成文を監視して、収益化表現が混ざったら投稿候補から外します。

確認が済んだら `enabled` を `true` にし、`links` を埋めてください。

## 手で動かすとき

```bash
npm ci
export GITHUB_TOKEN=...    # 公開リポジトリを読むだけなのでスコープ無しで可
export GEMINI_API_KEY=...

npm run feedback -- --dry-run            # ⓪ 反応の記録を取り込む（保存しない）
npm run archive -- --dry-run             # ⓪' 終わった週を履歴へ（保存しない）
npm run collect                          # ① 収集
node scripts/build-profiles.mjs --limit 3  # ② 理解（まず3件で試す）
node scripts/capture-media.mjs --repo Typa # ③ 素材（1件で試す）
npm run generate -- --dry-run            # ④ 生成（保存せず画面に出す）
npm run note:repo -- --dry-run           # ①'' 用意された記事を見にいく（保存しない）
npm run note:repo -- --repo KANJI_Town   # 1件だけ取り込む
npm run lint:drafts                      # 検査
npm run build                            # ⑤ ランチャー用データ＋アプリ一覧＋SWの版
npm run serve                            # http://localhost:8000 で確認
npm run check                            # 品質ゲート
npm test                                 # テスト
```

`npm run build` は3つをまとめたものです。個別にも呼べます。

```bash
npm run build:index   # docs/launcher.json
npm run build:apps    # docs/apps.html
npm run build:sw      # docs/sw.js の VERSION を中身から決めなおす
```

**`build:sw` は必ず最後に**実行してください。Service Worker の版は
`docs/` の中身から計算しているので、先に走らせると直した画面が端末に届きません
（`npm run check` がずれを検出します）。

Chromium がうまく起動しないときは、既にある Chromium を指定できます。

```bash
CHROMIUM_PATH=/path/to/chrome npm run media
```

## 気をつける点

- **時刻はすべて JST。** GitHub Actions の cron は UTC です。日付の判定は必ず
  `scripts/lib/jst.mjs` を通してください。`npm run check` が違反を検出します。
- **60日ルール。** リポジトリに60日間なにも動きがないと、GitHub は定期実行を止めます。
  週次ワークフローが毎週コミットするので通常は止まりませんが、
  長期間ワークフローが失敗し続けたときは Actions のページで再有効化してください。
- **リポジトリ名を変えるとき**は `config/accounts.json` の `repoName` と
  `docs/manifest.webmanifest` の `id` / `start_url` / `scope` を必ず揃えてください。
  `gigayama.github.io` は多数のアプリが同一オリジンを共有しているため、
  ここがずれると別アプリと取り違えられます。`npm run check` が検出します。

詳しい操作は [MANUAL.md](MANUAL.md) に書いてあります。
